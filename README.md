# Editor

Windows 11向けの文章Editorを、RustとSlintで開発するプロジェクトです。

現在は本体実装前の技術検証段階です。横書きソース編集と、DirectWriteによる縦書きライブプレビュー編集を切り替えて使用する構成を検証しています。

## 現在の検証アプリ

- 標準は横書きまたは縦書きの単一編集面で、非選択側のUIと再描画を停止
- 横書きモード: DirectWriteで組版したMarkdownソース編集。原文をそのまま描くので位置の対応表は恒等写像
- 縦書きモード: DirectWriteで組版し、Direct2D/WICで描画したライブ編集
- 両ペインとも同じブロック分割・タイル構造で、流れ軸だけが画面xと画面yに分かれる
- Rust側の共有文書バッファを正本とし、表示モード切り替え時に選択側だけを構築
- 任意のSplit表示では横書きと縦書きを同時表示し、原文変更を即時同期
- 行数、本文文字数、ソース文字数の表示
- 表示倍率の変更とステータスバー表示
- DirectWriteによる縦書きレイアウト、実描画、ヒットテスト、キャレットの検証
- 文書を論理行境界でブロックへ分割し、表示領域と交差するブロックだけを扱う構造
- ブロックの大きさは行が占める空間で数え、切れ目は行の内容そのもので決める
- 画像タイルはブロックの分割単位。識別子に座標を含めないので、文書幅が変わっても本文の変わらないタイルは再利用される
- ウィンドウサイズへの追従。列の高さはペイン高さ、タイルの大きさは「面積一定」で決まる
- リサイズは150ms、Markdownの展開行は120ms待ってから再レイアウト
- 縦書き面からの基本キー入力、削除、キャレット移動とMarkdown原文への反映
- 縦書き面のドラッグおよび`Shift+カーソルキー`による範囲選択、選択文字数表示、選択範囲への入力・削除
- 縦書きの`Home/End`による表示列端への移動と、`Ctrl`・`Shift`修飾
- 横書き面の入力、IME、キャレット移動（左右で1文字・上下で1行）、`Home/End`、削除、ドラッグ選択、縦スクロール
- Split時の境界線のドラッグによる左右幅の変更
- 描画フレーム時間とタイル転送量の計測（`set_rendering_notifier`）

縦書き編集面は、DirectWriteの縦書きレイアウトをDirect2DでWICビットマップへ描画し、RGBA画像としてSlintへ渡しています。全角英数字は正立し、連続する半角英数字は横組みのランを90度回転した形で表示されます。縦書き面をクリックすると、DirectWriteのヒットテストで文字位置を求めて横向きのキャレットを表示します。通常キー、矢印、Backspace、Delete、日本語IME、ドラッグ範囲選択による編集は共有Markdown原文へ反映されます。任意の字間・列間調整は未実装です。

## 構成

| ファイル | 役割 |
| --- | --- |
| `src/main.rs` | Slintとの接続、編集操作、キャッシュ管理 |
| `src/directwrite_render.rs` | DirectWrite/Direct2Dによる組版・描画・ヒットテスト。縦横どちらの書字方向でも動く |
| `src/text_blocks.rs` | ブロック分割・境界の決定・タイルの切り出しと座標計算。書字方向にも DirectWrite にも依存しない |
| `src/document.rs` | Markdown原文と整形後プレビューの対応 |
| `ui/app-window.slint` | 画面構成 |

`text_blocks.rs`と`document.rs`はWindows APIを使わないため、他の環境でも単体で検証できます。幾何計算やインデックスを追加する場合は、可能な限りこちら側へ寄せてください。

`text_blocks.rs`の座標は**流れ軸**（行が積み上がり文書が伸びる方向）で表します。縦書きでは画面のx（右から左）、横書きでは画面のy（上から下）です。直交する**行軸**は1行が走る方向で、長さはペインが決めます。このモジュールが知るのは`FlowOrder`——読み順が流れ軸の大きい方へ進む（横書き）か小さい方へ進む（縦書き）か——だけで、どちらの画面軸に割り当てられているかは知りません。

分割・タイル・キャッシュには、崩すと静かに性能が落ちる前提がいくつかあります。触る前に[技術検証](技術検証.md)の3.4と4.2〜4.5を読んでください。要点は3つです。タイルの識別子に座標を含めないこと、ブロックの大きさを自分の計測値だけから決めること、分割規則に文書先頭からの累積を持ち込まないこと。

横書きペインはSlintの`TextEdit`をやめ、縦書きと同じengineへ載せました（技術検証 3.7、置き換えの理由は6.4、結果は6.6）。Splitの最速フレームは89.98msから0.33msになりました。

両ペインは1つの文書を共有し、キャレットと選択はそれぞれが持ちます。**この2ペイン構造には、engineの正しさとは別に落とし穴が3つあります**（技術検証 6.7）。ペインが保持する位置は他ペインの編集後に文字境界へ丸めること、ペインは可視になった時点で生成されるので寸法を変化イベントだけに頼らないこと、入力の握り状態を自前のフラグで持たないこと。いずれも自動テストが全て通ったまま画面で発覚しました。

## 開発環境

- Windows 11
- Rust stable（MSVC）
- Slint 1.17.1
- windows-rs 0.62.2

## 実行

```powershell
cargo run
```

性能確認は最適化を有効にして実行します。デバッグビルドでは文字列処理の所要時間が実態より大きく出ます。

```powershell
cargo run --release
```

実行すると、`refresh_preview`の内訳が1操作1行で`perf_log.txt`へ追記されます。ステータスバーには要約だけを表示しています。ボトルネックの推定は繰り返し外れたので、手を入れる前にこのログを見てください。

## 検証

```powershell
cargo fmt --check
cargo check --offline
cargo test --offline
```

`run_check.bat`をダブルクリックすると上記を順に実行し、結果を`check_output.txt`へ書き出します。

依存パッケージをまだ取得していない環境では、最初の`cargo check`または`cargo build`にネットワーク接続が必要です。
