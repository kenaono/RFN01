# Editor

Windows 11向けの文章Editorを、RustとSlintで開発するプロジェクトです。

技術検証は完了し（[技術検証](技術検証.md) 8章）、[要件定義](要件定義.md)に沿った本体実装に入っています。1つのウィンドウの中で編集領域を分割し、各ペインがタブを持ち、タブごとに横書き／縦書き × ソース編集／ライブプレビュー編集の4モードを切り替えます（要件 7.2）。組版はどのモードでもDirectWriteです。

## 現在できること

要件の節ごとに、**動いているもの**を並べます。未達は最後にまとめてあります。

**作業フォルダとファイル（5）**

- 作業フォルダを開き、左ペインにファイルツリーを表示。展開状態はセッションへ
- **前に働いていた作業フォルダへ戻れる**（要件 5.1）。☰ の `Recent Folders` が10件を新しい順に出し、
  名前はそれを入れているフォルダと並べて書く（`50_Dev — 10_Creation`）——`notes` という名の年が何年ぶんもあるため。
  **いま開いているものは並ばない**：1つのウィンドウに作業フォルダは1つなので、この一覧は「行ける先」の一覧である。
  無くなっているフォルダを選んだときは、開かずに一覧から落とす（起動時に一件ずつ`is_dir`を訊きにいくと、
  切れているネットワークドライブが1つあるだけで起動が止まる）
- **一覧を出す行は`show()`が先、`close()`が後**（6.24）。行に`if`を付けた時点でそれは繰り返し要素で、
  先に閉じるとハンドラが走っている当の要素ごと消える。`Typography…`が逆の順で動くのは`if`の外にあるから
- ファイルとフォルダの新規作成・名前変更・複製、ごみ箱への削除、エクスプローラーで表示
- **ツリーの中はドラッグで動かせる**（要件 5.2）。行を掴んで4px動かすと運搬が始まり、それ未満は
  今までどおりの選択。受け取れるのは**フォルダの行**と**パネルの見出し**で、見出しは作業フォルダ
  そのものの名前——**行と違ってスクロールで消えない**ので、根へ戻す道が常にある（6.25）。
  **光る場所と落ちる場所は同じ3つの規則**で決まる：ファイルの行、いま入っているフォルダ、
  自分自身とその下（`subtree_end`）は初めから光らない。**列は手の下で描き直さない**——移動は
  手を離してから`Timer`で1回（6.18・6.24）。運び込まれたフォルダは開かれ、開いているタブは
  名前変更と同じ道（`move_entry`）で追従する
- **比べるのは一覧の中の座標**で、画面の座標ではない。行は自分の`y`を知っていて、運ぶ点も
  「掴んだ行の`y` ＋ 行の中でのマウス位置」で作るので、両辺が同じ物差しに乗る。
  **`absolute-position`は使わない**——`opacity`を持つ要素ではSlintが`Opacity`で包み、
  行の位置を二重に数える（6.26）
- **名前を変えても、開いているタブはその文書のまま追従する**。フォルダを変えれば下にあるファイルも
- エクスプローラーで表示は、ツリーで選んだものと、いま編集している文書のどちらからでも
- 開いていないフォルダは読まない。ツリーから開いたファイルが既に開いていれば同じ文書を共有する
- **ファイルへの操作は行のもの**——行の`…`と右クリックが同じメニューを出す。行を持たない
  「新規ファイル」「新規フォルダー」だけがパネルの見出しにある（空のフォルダには訊く行が無いため）

**画面（6）**

- 左ペインは Explorer・検索・履歴・アウトラインの4つ。**アイコンの縦列で切り替え、列は左ペインを閉じても残る**
- 編集領域を右または下へ分割、解除、入れ替え。境界はドラッグで動かせる
- 各ペインがタブ列を持ち、タブごとに4モードと表示倍率を覚える
- タブは名前と未保存のドット、前に出ているものだけが×を持つ。**タブは縮まない**——入りきらないぶんは
  帯が横に流れ、前に出ているタブへ自動で寄る。帯の外にあるタブは右端の一覧（`⌄`）から名前で選べる。
  `＋`と`⌄`は帯と一緒に流れない位置に置いてある
- **タブはドラッグで並べ替えられ、別のペインへ移せる**（要件 6.5）。掴んで4px動かすと運搬が始まり、
  それ未満は今までどおりの選択（`clicked`をやめて押下・移動・解放を自分で追っている——クリックは
  「押した所で離す」ことで、運搬はまさにそうでない場合なので、同じ押下から両方が出るなら押下を追うしかない）。
  **手の下で列は並べ替わらない**——並べ替えは`publish_tabs`を通り、それはドラッグを握っている当の要素を
  作り替えることになる（6.18・6.24）。動かすのは印だけで、実際の移動は手を離してから1回
- **どのタブの上かはSlintが答える。**タブは名前ぶんの幅を持つので、幅を知らないRustには答えられない。
  全タブの座標をRustへ報告させると同じ問いへの2つ目の答えができるので、**各タブが自分の矩形と
  運搬中のxを比べて「私の上だ」と言う**。運搬の状態は**窓**が持つ——ペインは互いを見られないので、
  隣のペインは自分の上に何か来ていることを知りようがない。各ペインは自分が置かれた矩形と点を比べて
  自分で答え、**それは落下先を決める`drop_tab`と同じ判定**なので、画面が示す先と落ちる先が食い違えない
- **運び込まれる側は帯の色が変わり、末尾に縦線が出る。**色まで変えるのは、タブが入りきらない列では
  末尾がビューポートの外にあるから——**スクロールで消える指示は、ときどき無い指示である**（6.25）
- **1つの列に同じ文書は1枚**で、運び込んだほうが残る。要件6.4が分割時に同じファイルを新しいペインへ
  入れるので、**運び込む先には最初から双子がいる**。書き手が運んできたのはこちらの見え方
  （キャレット・スクロール・表示モード＝要件7.6）なので、双子のほうが消える。
  最後の1枚を運び出したペインは、閉じたときと同じく分割が解ける（要件 6.4）
- **視点を動かすのは代入で、命令と記録は別の口**（6.28）。`Flickable`は押された瞬間に`viewport-*`の
  束縛を捨てるので、一度クリックしたペインへはRustの書き込みが届かない——`scroll-generation`が
  進んだときに`scroll-to-x`/`scroll-to-y`を代入し直す。タブを戻したときの位置復元も、
  ファイルを開いたときの先頭表示も、キャレット追従もこの道を通る
- タブは1枚ずつ・他のタブ・すべての3通りで閉じられる。**「他の」と「すべて」はウィンドウ全体**で、
  `⋮`が乗っているペインが決めるのは「どの1枚を残すか」だけ（画面に出ているペインが対象で、
  分割を解除して隠れているペインのタブは残る）
- **保存を訊くタブが何枚あっても質問は1件ずつ**。答えが次の1枚を進め、キャンセルは残り全部をやめる
- **タブと編集ペインをキーボードで渡り歩ける**（要件 11.3）。`Ctrl+Tab`／`Ctrl+Shift+Tab`は
  **そのペインの帯の並び順**で次と前のタブへ移り、両端で回り込む。`Ctrl+Alt+←→↑↓`は
  その向きにあるペインへキーボードを渡す。**向きは画面の向き**で、ペインの中で文字が
  どちらへ流れているかとは関係がない——縦書きのペインが左にあれば、それは左にある。
  **どのペインが隣かは矩形が決める**（`pane_layout::neighbour`）。木ではなく、実際に描かれた
  場所どうしを比べる：向かい合う辺を一番多く共有しているペインへ移り、その向きに何も無ければ
  何も起きない（帯の両端と違って、編集領域の端は書き手に見えている）
- **`Esc`でメニューを閉じる。**キーボードはペインに置いたまま、キーのほうを渡す——メニューの中に
  `FocusScope`を置くと、外側のクリックで閉じたときに返す機会が無くなる（6.14）
- **ボタンはアイコンで、名前はマウスオーバーで出る**（要件 6.7）。アプリ全体の操作はトップバーのメニュー、
  ペインとタブの操作はそのタブ列右端のメニュー。**どのペインに効くかは、メニューがどのペインにあるかで決まる**
- 表示モードの切り替えだけはメニューへ入れずタブ列に出したまま。いまどのモードかが常に見えている必要があるため

**編集（7）**

- 両ペインでの入力・削除・キャレット移動・範囲選択・IME・ドラッグ選択・`Ctrl+A`
- **矩形選択（`Ctrl+Shift+Space`）**（要件 7.1・11.4、2026-08-28改訂）。4モードすべてで使える。
  **矩形は「表示行の範囲」×「行を横切る位置の範囲」**で、両端のキャレットが立っている位置から決まる。
  **もとは論理行で定めていたが、それではこのEditorが書くものの上で使えなかった**——Markdownの散文は
  1段落＝1論理行なので、画面で何十行に見えていても「下の論理行」は段落を終わらせる空行、その次は見出し。
  **書き手が囲もうとしているのは見えている行**である。要件定義§7.1をそう改めた
- **行を横切る位置は座標で、桁ではない**。engineが`rectangle_runs`で表示行を1本ずつ辿り、
  両端の座標で当たり判定を取る（`move_caret_by_line`がキャレットの縦移動で保つのと同じ座標）。
  **等幅を強制しないので桁では表せない**し、座標なら縦書きでもそのまま——線軸は縦書きならy、横書きならx
- **この改訂で整形表示がただで付いてきた**。表示行で定めるなら整形表示の矩形は整形表示のまま成り立つので、
  「選択にかかる論理行を原文に立ち上げる」必要が消えた（その定めも要件から外した）
- **コピー・切り取り・削除が矩形を見る**。渡すのは行を改行で繋いだもの（他のアプリが塊として貼り直せる形）。
  **取り出しは1回の変更**——最初の行の頭から最後の行の末までの範囲を、間の文字を残したまま入れ替えるので、
  20行の矩形でもUndoは1手（要件 7.1）。キャレットは矩形の手前の角に残る。
  **矩形を選んだまま打つと、まず矩形が消えてから1箇所に入る**——全行の同じ位置に同じ文字を入れる
  「矩形挿入」はどの要件も求めていない別の機能で、普通の打鍵の裏でそれをやるべきではない
- **矩形は組み上がった行の上で切る**。engineが組み直したあとに`lay_out_pane`が切って、
  ペインの行に**画面のUTF-16と文書のバイトの両方**で置く。コピーも切り取りもそれを読み返す
  ——同じ問いを2度訊けば2度答えうるので
- **語単位の移動（`Alt+F`／`Alt+B`）と選択の開始（`Ctrl+Space`）**（要件 11.4）。
  **語の切れ目は1つの規則で決まる**——「句読点でも空白でもない文字の連なり」。要件が
  「日本語では句読点または空白まで」と言っているのは、日本語が語のあいだに空白を書かないから
  であって、英語では空白が同じ仕事をしている。**言語を見分ける必要がない。**`_`は語の内側なので
  `snake_case`は1語。移動先は**ペインが組んだ文字列に訊く**ので、整形表示では隠れたマーカーは
  語のうちに入らない。矢印の±1/±2が流れ軸なのに対し、**語の±3は両ペインで同じ**——
  文字列の先にある語は、ペインがどちらへ流れていても先にある
- **`Ctrl+Space`は「押さえていないShift」**。入れているあいだは矢印もHome/Endも選択を伸ばす。
  もう一度押すと止まり、**そのとき選択は消えない**（`Alt+W`が次に押すキーなので）。
  編集とクリックでも止まる——どちらも作りかけの選択に答えたことになるから。
  読むのは`update_selection_after_move`1箇所だけで、移動が選択をどうするかを決めている唯一の場所
- **Kill Ring と、それを使う5つのキー**（要件 11.4・11.6）。`Ctrl+K`はキャレットから行末まで、
  `Alt+W`は選択を控え、`Alt+X`は抜いて控え、`Alt+Y`は最新のものを入れ、`Alt+Shift+Y`は
  **いま入れたばかりのものを1つ前のものに入れ替える**（続けて押すとさらに前へ、末尾まで行くと先頭へ回る）。
  **Kill RingはWindowsのクリップボードとは別**（要件 11.6）——`Ctrl+C`／`Ctrl+X`は向こう、
  `Ctrl+K`／`Alt+W`／`Alt+X`はこちら。書き手はプログラム間に1つ、段落間にもう1つ運べる。
  **`Ctrl+K`は行末にいるときは改行そのものを取る**。取らないと行末では何も起きず、
  2回押して「行を取る・隙間を閉じる」ができない。**`Alt+Shift+Y`は貼ったものがまだそこにあるときだけ効く**
  ——覚えているのは「どの位置にどの文字列を入れたか」で、文書がいまもそれを持っているかを訊く。
  だから他のすべての編集が「私がやった」と申告しなくてよい。入れ替えは削除＋挿入ではなく
  **1回の置換**なので、Undo1手で戻る
- **`Ctrl+D`は次の1文字を削除**（要件 11.4）。`Delete`キーと同じコールバックを通る——要件が求めているのは
  同じ行為であって、2つ目のやり方ではない
- **コピー（`Ctrl+C`）と切り取り（`Ctrl+X`）**（要件 11.2）。**渡すのは両端のあいだの原文**で、
  整形表示でも選択はソースのバイトで持っているので、貼り直せば元の文書に戻る。改行はCRLFで出す
  ——文書はLFだけを持ち、入ってくるときに対（つい）をほどいている。**切り取りはコピーの成否を待つ**：
  クリップボードを他のアプリが握っていることがあり、渡せていないのに本文から抜いたら、
  書き手が見ていない理由で失われる。抜くときは普通の削除を通るのでUndo1手で戻る。
  **貼り付けには経路が要らない**——`Ctrl+V`はIME用の欄に落ち、打鍵と同じ道で本文へ入る
- Undo／Redo。履歴は文書が持ち、差分だけを記録する（スナップショットは取らない）
- 文書内の検索・置換（`Ctrl+F`／`Ctrl+H`）。**バーはその文書を開いているペインの中**、タブ列のすぐ下に出る。
  **置換の段は`Ctrl+H`のときだけ**。**開いたのと同じキーをもう一度押すと閉じる**（検索欄に
  キーボードがあるときも同じ——`Field`が使わなかったキーを`shortcut`で外へ渡す）。`Esc`でも閉じる。
  置換は通常の編集経路を通るのでUndo1手で戻る
- ライブプレビューは見出しを大きく組み、**太字・斜体・取り消し線・インラインコードを表示する**。
  閉じないマーカーはマーカーとして扱わないので、`snake_case`も`2*3`もそのまま出る
- **Calloutはラベルを語として残し**（`> [!NOTE]` → **NOTE**）、**脚注は`^`だけを落とす**
  （`[^1]` → `[1]`）（要件 7.3.2）。どちらも枠や上付き文字にはならない——
  **プレビューは原文から削ることしかできない**ので（技術検証 4.12）、
  ページに無い語をページに置けない。Calloutの枠は引用の縦棒と字下げがそのまま担う
- **リンクは見せる語だけを出し、下線を引く**（要件 7.3.2）。`[説明](章/一.md)`も`[[ノート名|表示名]]`も。
  **色は付けない**——要件9が書き手に持たせるのは墨・紙・見出しの色で、**誰も設定できない色は
  いつか誰かの紙に合わない**。下線はどの紙の上でも読める。**画像は記法のまま**（要件 7.3.3）で、
  普通のリンクとして出すと絵であることが消えるので
- **コードブロックは等幅で組み、角の丸い地の上に載る**（要件 7.3.2）。フェンスの内側は設定の等幅フォントで、
  **中では何もマーカーにならない**——`**`も`#`も素通しで、アウトラインにも出ない。
  **フェンスの行（``` ）は箱で隠れる**が、行そのものは残るので、そのぶんが上下の余白になる。
  地は**ブロック全体でひとつの矩形**で、行ごとに描くと切れ目ごとに継ぎ目が出て角も丸められない
- **箇条書き・番号・タスクは字下げされ、行頭に`•`／`☐`／`☑`と番号が出る**。`-`も`10.`も`- [x]`も
  同じ字下げから始まり、**折り返した続きの行もその頭に揃う**（要件 7.3.2）。
  **入れ子になった項目は一段ぶんずつ深く入る。深さはその項目が下にいる項目から決まる**
  ——書き手は2字でも3字でも4字でも下げるので、桁数を固定の数で割る規則ではどれかが必ず外れる。
  字下げの空白はマーカーと一緒に箱の下に隠れる（それ自体が幅を取ってはいけないので）。
- **項目の下に字下げして書いた段落は、その項目と同じところに揃う**（要件 7.3.2）。項目ではないので
  記号は付かず、**強調も見出しも普通に効く**——素通しではなくなった。どの項目の続きかは
  **その左から始まる最後の項目**で、それより深く下げても同じ項目に揃う
  **字下げはブロックのもの**で、記号は溝に描く——箱は論理行の頭にしか置けないので、
  箱に幅を持たせるかぎり1行目しか動かせない。**項目の連なりが1ブロック**で、項目ごとには切らない
  （切ると、リストばかりの文書でブロックが6倍になる。実測は技術検証 7.1）
- **引用は段落ごと字下げされ、その脇に縦棒が立つ**（要件 7.3.2）。折り返した続きの行も含めて全部が揃う。
  **字下げはブロックのもの**——行の頭に置く箱では1行目しか動かせないので、引用の連なりを1ブロックにまとめ、
  そのブロックを狭く組んで寄せている。深さ1段につき1本、棒はその段の溝に立つ
- **`---`には罫線**（要件 7.3.2）。縦棒と同じく**文字範囲ではなく論理行そのものの矩形**に描く。
  `---`／`***`／`___`そのものは箱で隠れる
- **表は升目に組む**（要件 7.3.2）。外枠があり、行と行のあいだにも列と列のあいだにも罫線が入り、
  **見出しの行は太字**。列は**いちばん広いセル**の幅で、ペインに入らなければ**按分で縮み**、
  **入らないセルは列の中で折り返す**（行はその行のいちばん高いセルの高さになる）
- **表は「1ブロック＝1レイアウト」でない唯一のもの**（技術検証 7.7）。**セルそれぞれが自分の
  レイアウトを持つ**——折り返した行はセルAの2行目とセルBの2行目が横に並ぶ必要があり、
  1つのレイアウトの中の文字順はA→B→Cなので、どう組んでも並べ替えられないため。
  `TableGrid`がセルの箱・罫線の位置・揃えを持ち、**キャレット・クリック・選択・上下移動・描画の
  5箇所が同じ升目を通る**（インクとキャレットが同じレイアウトを見ていることが全部）
- **表は自分だけのブロックを持つ**。表と段落が同じブロックにいると、2通りの組み方を同時にすることになる
- **揃え（`:---`／`---:`／`:---:`）はセル自身の`SetTextAlignment`**。セルが自分の箱を持つので、
  余りを前の箱に運ばせる必要が無い
- **区切り行（`|---|---|`）は何も出さない**。見出しの下の線は、他の行の境と同じ罫線として引かれる。
  **カーソルがその行に来れば立ち上がって`| --- | --- |`を見せる**（要件 7.3.1）。表のどの行も同じで、
  カーソルのある行は**1つのセル**になって原文を出す——そのときも**列は動かない**（幅は測ってあるので）
- 作業フォルダ全文検索、最近開いたファイルの履歴、見出しからのアウトラインと移動。
  **全文検索は別スレッド**（要件 2）——編集器が一度に多数のファイルへ触る唯一の場所で、
  かかる時間を決めるのは開いたフォルダであって編集器ではない。答えはイベントループ経由でだけ戻り、
  **打ち直された古い問いへの答えは捨てる**。走っている検索も、新しいものが来たらファイルの切れ目でやめる
- **検索は英字の大文字・小文字を区別しない**（文書内も作業フォルダ全体も）。畳むのはASCIIの範囲だけで、
  全角Ａとａ、アとあは別の文字のまま——**畳んでも長さが変わらないことが、バイト位置をそのまま返せる理由**

**保存と復元（8）**

- 入力停止2秒／継続でも5秒ごとに、アプリ専用領域へ作業コピーを退避。書き込みは別スレッド
- `Ctrl+S`は確認なしで上書き。外部変更と競合したときだけ4択で訊く
- `Save All`は開いている文書をまとめて書く。**ファイルが決まっているものを先に黙って書き、
  無題の保存先はそのあとで訊く**（最初のキャンセルで残りは訊かない）。**外部で変更された文書だけは
  書かずに数を伝える**——要件8.3の4択を黙って飛ばすわけにはいかず、作業コピーが持っているので待てる
- 未保存の新規バッファを「無題1」「無題2」として保持し、終了しても破棄しない
- 起動時に、作業フォルダ・分割・タブ列・モード・キャレット・選択・スクロール・表示倍率を戻す
- **表示設定はアプリ専用領域の`settings.rfnsettings`へ**（要件 9）。1行1設定の`名前: 値`で、
  **色は`#rrggbb`のまま**書く——人が読んで直せる形が、この規模で要る唯一の書き出しなので。
  知らない名前は読み飛ばし、無い名前は既定のまま。数値は読むときもボタンと同じ範囲へ収める
- **作業を失いうる質問は、Windowsのメッセージボックスではなくウィンドウの中に描く**（要件 8.3・8.4）

**表示と文書情報（9・10）**

- **表示設定は横書き・縦書きの2枚のシート**（要件 9）。**シートに載っている値は全部その向きのもの**なので、
  どれがどちらに効くのかを覚える必要がない
- 各シートは、本文とH1〜H6の**それぞれについてサイズ・文字色・フォントを1行で**持ち、
  行の送り（横書きなら行間、縦書きなら列間隔）・文字送り・余白・紙の色・等幅フォントを持つ。
  **色見本を押すとWindowsの色ダイアログ**、フォントの欄を押すと**インストール済みの一覧**が出る
- **原文（ソース編集）には文字の設定が効かない**——一様な大きさ・色・書体で出る。
  記法そのものを読み書きする面で、見出しが大きく色づくのは編集の助けにならないため。
  行の送り・文字送り・余白・紙の色はシートのものを使う
- **コードのコメントは自分の色で出る**（要件 7.3.2）。フェンスが名乗った言語だけが対象で、
  名乗らないブロックには何も付かない。**色は設定ではなく、書き手の墨を書き手の紙のほうへ寄せた色**
  ——要件 9 が自由にしたのは墨・紙・見出しで、誰も設定できない色は誰かの紙に合わない
  （リンクに下線だけを引いているのと同じ理由）。文字列の中の`//`は見ない（`"https://…"`が
  色づくのが、この単純さが露見する唯一の場所）。**整形表示だけ**——原文の面は書いたとおりに見せる面
- **原文には字下げも飾りも付かない**（要件 7.3.1）。箱・引用の字下げ・縦棒・罫線は**整形表示だけのもの**で、
  記法の代わりに立つものだから。原文には`>`も`---`もそこにあり、上に重ねれば同じことを二度言うことになる
- **表示倍率は編集ペインごと**（要件 9・11.5）。`Ctrl+ホイール`は**ポインタが乗っているペイン**を拡大縮小し、
  `Ctrl+=`／`Ctrl+-`／`Ctrl+0`はキーボードを持っているペインに効く。**ホイールはフォーカスを動かさない**——
  指しているペインを大きくすることと、打ち込む先を変えることは別のこと。
  50%から240%までを10%刻みで、ステータスバーはフォーカス中のペインの倍率を出す。
  ペインごとの倍率はセッションへ入り、**タブを切り替えても変わらない**——倍率はそのペインを読んでいる距離であって、
  文書の性質ではない
- 行数、本文文字数、ソース文字数、選択文字数の表示（3桁ごとに区切る）。長すぎる段落の警告だけが赤い
- **クイック下書き**（要件 12）。`☰ Quick Draft…`で開く別窓で、**`Enter`は常に改行**——チャットへ送る短文を
  誤送信なしで推敲するためのもの。プレーンテキスト1面だけで、Markdownも縦書きも無い。
  `Ctrl+C`は選択、`Ctrl+Shift+C`と`Copy all`は全文。`On top`で常に手前、位置と大きさは覚える
- **送信ボタンは送り先のタブ名**（要件 12.4）。**クリックでそのタブへ貼って窓を閉じ、押したままにすると
  一覧が出て、選んで手を離すとそこへ貼る**。送り先は前回選んだタブを覚え、一度も選んでいなければ先頭。
  **覚えているタブが閉じられていたらクリックで一覧を出す**——別のタブを勝手に選ばない。
  一覧のペイン番号は左右でも上下でもなく番号（分割は今後増える）。
  **覚えるのは「ペインと文書」の組**——要件 6.4 は2つ目のペインを1つ目と同じ文書で開くので、
  ふつうの状態では1つの文書が2つのタブにいる。文書だけでは後に当たったほうが選ばれる。
  **押している間、行の当たり判定は`mouse-y`の算術**——押しているボタンがポインタを掴んだままなので、
  行はホバーを受け取れない。行の高さは`row-height`1つで、一覧の高さも当たり判定もそれで測る
- **下書きは出ていったら空になり、履歴に10件残る**（要件 12.4、2026-08-27改訂）。
  `Clear`・`Paste to tab`・窓を閉じる、のどれでも**必ず履歴へ入れてから空にする**ので、
  何をしても本文は失われない。`History`から選べば戻る。新しいものが先頭、同じ本文は1件。
  置き場所は`%LOCALAPPDATA%\RFN Edit\`の`draft.rfndraft`と`draft-history.rfndrafts`で、
  **履歴は区切り文字ではなく長さで持つ**——下書きはどんな行でも含みうる
- **キャレットの行と桁は`Ln 12, Col 5`で、ソース編集のときだけ出る**（要件 10）。行はファイルの改行で数えた
  論理行、桁は書き手が見える文字で数えた位置（絵文字1つは1桁）。**整形表示には出さない**——あちらの
  キャレットは記号を抜いた本文の中にいるので、そこで数えた桁はファイルに無い場所を指す

**性能まわりの構造**

- 文書をブロックへ分割し、表示領域と交差するブロックだけを扱う。改行の無い長大な段落はDirectWriteの折り返し位置で切る
- **ブロックの計測と折り返し位置の探索は複数スレッドに分かれる**（要件 2）。ブロックは自分のテキストだけで
  測れるので分割でき、長大段落どうしも独立している。効くのは幅や表示設定が変わったときの全再計測で、
  **1打鍵は1ブロックしか測らない**。perfログの`measured=全部/分けたぶん`と`wrap=訊いた/そのまま/再開/分けた`
- **表も1打鍵に1つも測り直さない**（要件 7.3.2、技術検証 7.9）。列幅はセルを1つずつ組んで測るので
  25行の表1つで1.13msかかり、**2026-09-06まではキャッシュの外にいて、文書の中の表の数だけ毎打鍵払っていた**
  ——章立ての表を16こ持つ構成表で1打鍵20.8ms。いまは他のブロックと同じ鍵で引き、**変わった表だけを測る**。
  鍵にはキャレットがどの行にいるかも入る（要件7.3.1でその行だけバーが見えるが、その箱はrunsではなく
  計測が作るので、runsの違いとしては現れない）
- **1打鍵の実測**（技術検証 7.9）。295KB・表16こで**2.55ms**、上限の100万字で**15.25ms**（1ペイン）。
  内訳のいちばん大きいところは`TextEngine::update`で、残っているのは**文書全体に比例する仕事**
  ——分割・全ブロックの鍵・折り返す項目の数え上げ。これは「engineが文書を丸ごと受け取る」という
  前提そのもので、9.1に分けてある
- **タイル描画は分かれない**（要件 2、技術検証 7.8）。作って測って戻した——**28コアで8スレッドは1スレッドの
  7倍かかる**。Direct2D/WICのラスタライズはファクトリをスレッドごとに分けてもプロセスの中で1本に並ぶ。
  組版が5.9倍になったことは描画について何も言っていなかった。**タイルは`TileTask`という parcel と
  `draw_tile`のまま残してある**——engineを触らずに描く形そのものが読みやすく、そして測りやすい
- **折り返し探索は「訊く・答える・使う」に割ってある**。分割を1回**何も答えずに**走らせてどの行を訊かれるかを
  記録し、答えをスレッドで見つけ、表を引きながら分割し直す。**訊くのが、どの行が長すぎるかという規則の複製を
  持たずに知る唯一の方法**で、複製は「ブロックがどこで終わるか」についての第二の意見になる。
  **長大段落を持たない文書は分割1回で終わる**（何も訊かないので）
- ブロックの大きさは行が占める空間で数え、切れ目は行の内容そのもので決める
- 画像タイルはブロックの分割単位。識別子に座標を含めないので、文書幅が変わっても本文の変わらないタイルは再利用される
- **タイルは1度だけ書かれ、追い出されたタイルの2MBは次のタイルが描かれる場所になる**（`TileSink`／`spare`、技術検証 7.8）。
  **画素を置く場所を作るほうが画素を描くより高い**——`SharedPixelBuffer::new`が0.72msに対し、
  ラスタライズは0.31ms。触ったことのあるページに書き直せば、その0.72msは消える（16枚で17.8ms→7.2ms）。
  使い回しは原理的に安全で、まだ誰かが握っているバッファはSlintが勝手に複製する（`SharedVector::detach`）
- リサイズは150ms、Markdownの展開行は120ms待ってから再レイアウト
- **窓の位置と大きさも覚える**（要件 8.5）。最大化されていたかも別に覚え、位置のほうは
  **最大化・最小化されていない最後の姿**を書く——最大化した大きさで復元された窓は、元に戻せない。
  画面に載らない大きさ（16384px超）は拒むが、**位置は直さない**：画面の外へ出た窓はドラッグ1回で戻せる一方、
  どのモニタのつもりだったかを当てにいくほうが害が大きい
- **セッションが覚えるのは「上端にあった文字」で、画素位置ではない**（要件 8.5）。画素は幅・拡大率・
  モードが変われば別の場所を指すが、起動中はその3つが後から届く——**復元したスクロールは窓が落ち着く
  までに何度も無意味になり、キャレット追従に上書きされていた**。いまは`ViewAnchor`が「その文字を
  上端に置く」を毎リフレッシュやり直し、**キャレットが動いたら手を引く**（それが書き手の
  「そこではない」）。タブの切り替えでも同じ問題が起きるので、同じ道を通る
- **重い文書では、打鍵ごとに組まない**（`EditPace`、要件 2）。**本文は待たせず、描画だけを待たせる**——
  重かった描画のあとはかかった時間と同じだけ待ち（最大200ms）、その間の打鍵はまとめて1回で描く。
  キーリピートは毎秒30文字ほど届くので、1回40〜80msの文書では入力のほうが速く、
  **全部描こうとするとイベントループが戻らず「固まって見える」**（文字はすべて入っているのに）。
  軽い描画（8ms以下）と、手を止めたあとの1文字目は素通しする。perfログの`held=`が、
  1回の描画が運んだ打鍵の数
- 描画フレーム時間とタイル転送量の計測（`set_rendering_notifier`）と、段落長を倍々に振った計測用文書の生成

**折り返し幅（要件 9）**

- **1行の長さを、ペインの幅か、書き手が決めた文字数かで選べる**。`⋮ Typography…` の `Wrap`。
  **文字数で持つ**のは、画素で持つと字の大きさや表示倍率を変えるたびに1行の長さの意味が変わって
  しまうため（`text_blocks::line_extent_for_cells`は`cells_per_line`の逆関数で、往復がテストにある）
- **ソース編集にも効く**。要件9が原文から取り上げるのは文字の飾りだけで、1行の長さは面の読みやすさである
- **折り返さないこともできる。**`Wrap` の `Width` と `Pane` は**両方は入らない2つのスイッチ**で、
  **どちらも入っていない状態が「折り返さない」**（光っているほうをもう一度押すと消える）。
  1行はどこまでも1行で、**紙は文書のいちばん長い行と同じ幅**になる——その幅は行ごとにDirectWriteが
  測った値の最大に、ブロックの字下げを足し、余白で挟んだもの
- **指定幅もペインの幅に縛られない。**ペインより広く指定したら、入りきらないぶんは**横へスクロール**して
  見る（キャレットもその向きに追いかける）。ペイン幅で止めていた版は、25字しか入らないペインで
  25字と40字が同じ絵になり、**設定が効いているか画面から確かめようがなかった**（6.27）
- **タイルは交差軸にも切る**（要件 9）。1枚は流れ方向に`TILE_TARGET_PIXELS/幅`、交差方向に最大2048px。
  **ペインに収まる紙は1枚のまま**——折り返す文書のタイルの切られ方は前と1画素も変わらず、
  紙がそれより広いときだけ切れ目が入り、**画面に出ている列だけを描く**
- **1行N字に要る幅は`N×字送り + 2×margin_for(font_size)`**（実測。`margin_for`＝`max(1.5×font,16)`）。
  ペインに残って見える余白はこの紙の余白で、次の1字はそこには入らない
- **紙が狭いときは中央、広いときはスクロール**。この2つは`page`の`x`/`y`の`max(0px, …)`1つで両立する
- **狭いときは紙がペインの中央に立つ。**中央寄せは`page`の`x`/`y`**1箇所だけ**——タイルも選択も
  キャレットもIMEの位置も、報告を返すポインタも、その矩形の中にある。**動かすのは紙のほうで、
  中にいるものは誰も自分が動いたことを知らない**

**入れないと決めたもの**

要件2に対して残っていた4つは、**2026-09-06に全部「入れない」で閉じた**。どれも
**費用に対して買えるものが小さい**という同じ理由で、**入れる条件のほうを書いてある**——
その条件が来たら開き直せばよく、来ないうちは開かない。

- **長い段落の折り返し探索は、1打鍵の待ちとして残す**（要件 2）。費用は**編集位置から段落の終わりまでの文字数に比例**し、1文字約2.3µs——35,000字の段落なら、頭のほうを直すと77ms、終わり近くなら7.6ms（技術検証 7.4）。**日本語では前回の折り返しを流用できない**：均一な文字送りでは挿入した分だけ以降の行頭が永久にずれ、編集より後ろの行は「ずれた」のではなく別物になる（19か所で試して一致0）。残る道は「画面より下を手が止まるまで後回しにする」ことだけで、**それは編集している段落より後ろが手を止めるまで古い位置に居ることを意味する**（次の見出しがずれたまま居座る／スクロールバーの長さが前回の見積もり）。**書き手が実際に報告した症状（キーリピートで固まって見える）は`EditPace`が古い絵を1枚も見せずに解いている**ので、残る利益は「何万字もの1段落の頭のほうを直しているとき」だけになった。**入れる条件**：`EditPace`でも足りない文書が実際に出てきたとき
- **タイル描画はUIスレッドに残す**（要件 2）。**分けられないことは実測で決着している**（技術検証 7.8——8スレッドは1スレッドの7倍かかる）ので、残る道は「分ける」ではなく「待たない」——1本の描画スレッドへ出して届いたタイルから貼る形。**キャレットはSlint側の四角で、組版は待たせないので先に進む**。つまり**打つたびに、キャレットが1フレームぶん本文より前に出る**。外れる待ちは1打鍵あたり3.6msで、**もともと1フレーム（16.7ms）に収まっている**（実測`refresh total=4.06 tiles=3.57 tiles_new=1`）。**入れる条件**：1打鍵で描き直すタイルが1枚では済まなくなったとき（`tiles_new=`）
- **ファイル読み込みはUIスレッドのまま**（要件 2）。上限いっぱい（75万字・1.77MB）で3〜8ms、実際の文書（229KB）で0.4ms。開くのは操作1回につき1度で、1打鍵の2.5msに対して足りない待ちのために非同期の道を1本増やすほうが高くつく（技術検証 7.4）
- **空行を挟むリストは連なりが切れる**（要件 7.3.2）。空行は字下げを持たない行なので、項目・空行・項目で
  ブロックが3つに割れる。**見た目は正しい**（空行に描くものは無い）ので個数だけの話で、
  実測ではその個数は安い——`layout=`は文字数に付いていてブロック数には付いていない（技術検証 7.1）

縦書き編集面は、DirectWriteの縦書きレイアウトをDirect2DでWICビットマップへ描画し、RGBA画像としてSlintへ渡しています。全角英数字は正立し、連続する半角英数字は横組みのランを90度回転した形で表示されます。縦書き面をクリックすると、DirectWriteのヒットテストで文字位置を求めて横向きのキャレットを表示します。字間・列間・見出しサイズは表示設定（`☰ Settings…`／`⋮ Typography…`）から変更できます。

## 構成

**1つの実行ファイルです。DLLには分けません**——理由と、代わりに切るならどこか（ワークスペースのクレート、
その順番は要件2のあと）、そして**将来Terminalを内包するときの線**は[技術検証](技術検証.md) 9.3にあります。

| ファイル | 役割 |
| --- | --- |
| `src/main.rs` | Slintとの接続、編集操作、キャッシュ管理 |
| `src/directwrite_render.rs` | DirectWrite/Direct2Dによる組版・描画・ヒットテスト。縦横どちらの書字方向でも動く |

### 見た目

**入力欄とボタンは`ui/controls.slint`の`Field`と`TextButton`です。**`LineEdit`と`Button`は
選択中のwidget styleが描き、その`Palette`は全部`out`プロパティなので**紫にはなりません**（技術検証6.22）。
どちらも中身はSlintの組み込み（`TextInput`）のままで、箱だけを`Tok`で描いています。
**質問の答えは、Rustが並べた順の逆に描きます**——逃げ道が左、頼んだことが右。押されたときに送り返す
番号は位置から計算するので、Rust側の「最初が実行・最後が逃げ道」（Escは最後を選ぶ）は変わりません。
**どれが「失う」ボタンかはRustが番号で伝えます**（`question-danger`）——ラベルの文字で判定すると、
言い回しを変えた瞬間に壊れるので。

**色は`ui/tokens.slint`が正です。**画面のどこにも色を直接書かないでください——以前は18種類が
ばらばらに書かれていて、同じ意味の2箇所が気づかれずに離れていきました。

見た目の設計はキャンバスにあります（2026-08-22にユーザー承認で確定）。
<https://claude.ai/code/artifact/f3062bee-d934-4714-a627-7568f042f32e>
元のファイルは`design/`にあり、直すときはそこを編集して同じURLへ再公開します。

Slintのレイアウトで2回はまっているので、部品を足す前に技術検証6.23を読んでください。
**`alignment: start`を書くと伸縮子が効かず、レイアウトは溢れても切りません。**
どちらもコンパイルは通り、画面でしか出ません。**ただし「溢れても縮まない」は誤りでした**——
足りなければ`min`まで縮みます。`Text`のmin幅が文字幅そのものなのが原因で、
`overflow: elide`を付けると0になります（6.23）。

`text_blocks.rs`と`document.rs`はWindows APIを使わないため、他の環境でも単体で検証できます。幾何計算やインデックスを追加する場合は、可能な限りこちら側へ寄せてください。

組版の指定（`Typography`）は文書全体で1つ持ち、**行ごとに変わるのは見出しレベルだけ**です。プレビューではマーカーが除去済みでブロックが自分の文字から見出しだと知れないので、レベルは論理行ごとの配列（`StyledText`）として本文の横に並べて渡します。分割は論理行境界でしか起きないため、ブロックの属性は常にその連続部分列になります。行ごとにサイズが違っても「分割ブロックの合計＝単一レイアウト」が成立することは縦横とも確認済みです（技術検証 3.8）。**列間は必ず`PROPORTIONAL`で指定してください**——`UNIFORM`は全行の送りを1つの数値に潰し、しかも計算は合ってしまうのでテストに出ません（4.7）。

`text_blocks.rs`の座標は**流れ軸**（行が積み上がり文書が伸びる方向）で表します。縦書きでは画面のx（右から左）、横書きでは画面のy（上から下）です。直交する**行軸**は1行が走る方向で、長さはペインが決めます。このモジュールが知るのは`FlowOrder`——読み順が流れ軸の大きい方へ進む（横書き）か小さい方へ進む（縦書き）か——だけで、どちらの画面軸に割り当てられているかは知りません。

組版のコストは**測り直した文字数に比例します**（縦書き1文字3.26µs、横書き0.96µs、技術検証 6.9）。ブロック数ではなく文字数です。1打鍵をSplitで1フレームに収めるにはブロックが1,000字までで、`BLOCK_MAX_CELLS`の768セルがほぼそこを指しています。

分割・タイル・キャッシュには、崩すと静かに性能が落ちる前提がいくつかあります。触る前に[技術検証](技術検証.md)の3.4と4.2〜4.5を読んでください。要点は3つです。タイルの識別子に座標を含めないこと、ブロックの大きさを自分の計測値だけから決めること、分割規則に文書先頭からの累積を持ち込まないこと。

見積もりのうち`block_flow_bound`だけは、外すと性能ではなく表示が壊れます。DirectWriteへ渡すレイアウト箱の大きさなので、**下回ると行が切り落とされます**（4.8）。

改行を含まない長大な段落は、DirectWriteの折り返し位置で切ります（`WrapPoints`、技術検証 3.9）。**折り返し位置を探すには組版が要る**ので、段落ごとに位置を憶え、編集より前は前回の結果を使います。ここを素朴に書くと全長大段落を毎打鍵組版することになり、切る前より遅くなります（6.10）。

横書きペインはSlintの`TextEdit`をやめ、縦書きと同じengineへ載せました（技術検証 3.7、置き換えの理由は6.4、結果は6.6）。Splitの最速フレームは89.98msから0.33msになりました。

両ペインは1つの文書を共有し、キャレットと選択はそれぞれが持ちます。**この2ペイン構造には、engineの正しさとは別に落とし穴が3つあります**（技術検証 6.7）。ペインが保持する位置は他ペインの編集後に文字境界へ丸めること、ペインは可視になった時点で生成されるので寸法を変化イベントだけに頼らないこと、入力の握り状態を自前のフラグで持たないこと。いずれも自動テストが全て通ったまま画面で発覚しました。

**Undo履歴は文書が持ちます**（要件 7.1・7.6）。ペインではなく`OpenDocument`にあるので、同じファイルを2つのペインで開いていても履歴は1本で、どちらで`Ctrl+Z`を押しても最後の変更が戻ります。1エントリは「どこに・何があって・何が入ったか」だけで、文書の複製は持ちません——1文字ごとにスナップショットを取ると、このEditorが開く大きさの文書では毎打鍵メガバイト単位になります。打鍵が続いている間は1つのエントリに伸ばし、1.2秒の間があくか改行が入ると区切ります。**履歴が今の本文に合わなければ、当てずに捨てます**——外部変更の読み込みなどで本文が丸ごと入れ替わることがあり、覚えている位置が別のものを指している状態で当てるくらいなら、Undoできないほうが良いためです。

**同じものを2箇所に書くと、片方だけ直ります。**6.15も6.16もその形でした。そこで2ペインの違いは`PaneId`1つに集約してあります——流れがどちらの画面軸か、どのSlintプロパティを読み書きするか、その2つだけがあの`impl`の中にあり、組版・幾何・タイル・報告に加えて、入力・削除・キャレット移動・`Home`/`End`・IME変換中の表示もすべて共通の1本を通ります。編集系のコールバックは`PaneId`を渡すだけです。Slint側の`vertical`と対になる構造で、**ペインはモデルになりました（[ペイン分割設計](ペイン分割設計.md) 5）**——`PaneId`のアクセサは`screen`／`update_screen`、つまり`panes`モデル1行の読み書きです。行は読んで、変えて、書き戻します：スクロール・報告された寸法・IME欄はペイン自身が同じ行へ書くので、先に読んでおいた行は画面の行ではありません。

**作業を失いうる質問は、Windowsのメッセージボックスでは出しません**（要件 8.3・8.4）。メッセージボックスのボタンは「はい・いいえ・キャンセル」で固定なので、**どれが何をするかを上の段落で説明する**ことになります。作業を捨てるかどうかの問いを、段落を読ませて答えさせてはいけません。質問は`question-open`のオーバーレイとして画面に描き、選択肢はそれぞれのボタンに名前を持ちます。最後の選択肢が必ず逃げ道で、Escも外側のクリックもそれを選びます。**破棄はもう一度だけ単独で訊きます**——捨てる操作が残す操作の隣のボタンであってはならないためです。

副産物として、この形は**自前のメッセージループを回さない**ので6.18から構造的に外れます。代わりに質問は非同期になり、`Live`が「いま出ている質問」を持って、答えが来てから続きを実行します（`answer_question`）。

**このうち2つ目は、直したペインの隣で再発しました**（6.11）。Splitへ切り替えると縦書きペインは作り直され、生まれた時点で正しい幅なので`changed`が発火せず、幅が古いままになります。**ペインの寸法は必ず`init`でも報告してください。**両ペイン・両軸のすべてに当てはまります。

**それでも一瞬だけ古い値が残ります**（6.19）。すでに画面にあるペインはSplitの切り替えで作り直されないので`init`は走らず、`changed visible-width`が直すのはイベントループの区切りです。切り替えのハンドラがその場で走らせるrefreshは、それより前にあります。そこでRust側は、報告された幅を**ウィンドウが与えうる上限**で抑えます（`width_share_bound`＝ウィンドウ幅×そのペインの取り分）。上限であって代用ではないので定常状態では効きません。**ペインが自分について報告する値は、レイアウトが走る前の一瞬だけ嘘になります。**

**Slintのコンパイルは大きなスタックを持つスレッドで走ります**（`build.rs`）。ビルドスクリプトはWindowsの既定である1MBのスタックで動き、Slintのコンパイラは構文木を再帰で歩くので、`ui/editor-pane.slint`がそれを越えました。cargoが出すのは`STATUS_STACK_OVERFLOW`だけで、**ファイル名も行番号も出ません**——UIに悪いところは無く、読むための場所が足りていないだけです。

## 実行

```powershell
cargo run
```

引数にファイルを渡すと、そのファイルをタブで開いて起動します。`.md`をこの実行ファイルに関連付ければ、エクスプローラーでのダブルクリックがそのまま「ここで開く」になります。複数選択して開けば、指定された順にタブが並びます。存在しないパスは黙って無視します。

```powershell
cargo run -- README.md
```

性能確認は最適化を有効にして実行します。デバッグビルドでは文字列処理の所要時間が実態より大きく出ます。

```powershell
cargo run --release
```

実行すると、1操作1行の内訳が`perf_log.txt`へ書き出されます。ステータスバーには要約だけを表示しています。ボトルネックの推定は繰り返し外れたので、手を入れる前にこのログを見てください。

**出力先は実行ファイルと同じ場所です。**カレントディレクトリはフォルダを開くたびに動くので、以前は1日ぶんのログが見ていた場所へ散らばっていました。診断ログの`diag/`も同じ場所に作られます。

**ログは1回の実行ぶんだけを保持します。**起動時に前回のぶんを`perf_log.prev.txt`へ退避してから書き直すので、消してから実行し直す必要はありません。行の種類は7つです。

| 先頭 | 意味 |
| --- | --- |
| `session` | 実行の開始。`profile=debug`か`release`かはここにしか出ず、**読み方が変わる唯一の値**です |
| `sample` | 計測用文書の読み込み |
| `edit` | 1回の編集の全体。`refresh`が測り始める前の、文書の複製ぶんを含みます |
| `refresh` | 縦書きペインの1操作 |
| `horizontal` | 横書きペインの1操作。`refresh`と**同じ項目を同じ順で**出すので、2つのペインの値はそのまま並べて比べられます |
| `relayout` | 倍率や組版の変更。両ペインの全ブロックを計測し直すので、1打鍵とはコストの桁が違います |
| `resize` | ウィンドウサイズ変更後の再レイアウト。`pane=`でどちらのペインかを言います |

`refresh`と`horizontal`の項目名は**流れ軸で読みます**。`content`は文書が流れ軸へ伸びた長さ、`extent`は行軸のペイン幅——縦書きなら`content`が横幅で`extent`が列の高さ、横書きならその逆です。画面のxとyで名付けると同じ名前が2つの意味を持つので、そうしていません。以前の`width`/`height`はこの2つに分かれました。

## 診断ログ

`perf_log.txt`（こちらも**実行ファイルと同じ場所**で、リリース実行なら`target/release/`です——リポジトリ直下にも古い実行のものが残っているので、読む前に日時を見てください）が**費用**の記録なのに対し、`diag/Diag_<日付>_<時刻>_<番号>.log`（実行ファイルと同じ場所）は**出来事**の記録です。1回の実行につき1ファイルで、起動した時刻で名前が付くので上書きされません。性能ログが直近2回だけを残すのに対し、こちらは全部残ります——読みたい実行は最後の実行とは限らないからです。

1行は`+経過ms 種別 key=value ...`の形で、種別で絞れば1種類の出来事だけを抜き出せます。

| `refresh.h` / `refresh.v` | 1回の再表示。内容長・報告値・ブロック・タイル・キャレット |
| `pointer.h` / `pointer.v` | クリックとドラッグ。座標と、そこから得た文書位置 |
| `edit` | 1回の編集。どちらのペインか、文書の大きさ。Undo／Redoもここに出ます（要件 7.1） |
| `file` | 開く・保存の成否とパス |
| `work` | 作業コピーの退避・復元（要件 8.1） |
| `tab` | タブの追加・切り替え・クローズと、ドラッグでの移動（要件 6.5）。`move`＝同じ列の中、`carry`＝別のペインへ |

| `layout` | 境界のドラッグ。木がどう動いたか。`focus`はキーボードがどのペインからどのペインへ移ったか（要件 11.3） |
| `scroll.h` / `scroll.v` | スクロールで**新しいタイルを描いたとき**と、Rustが視点を動かしたとき（要件 8.5）。`apply to=… went=…`は「頼んだ位置」と「実際に着いた位置」で、**食い違ったらFlickableが押し戻している**（6.28） |
| `folder` | 作業フォルダを開いたとき（要件 5.1）と、ツリーの中の移動（要件 5.2）。`opened`＝そのフォルダへ移った、`gone`＝履歴から選ばれたが既に無かったので一覧から落とした、`move`＝運ばれた先、`drag`＝1回の運搬（押下・移動の回数・運搬になったか・落下先。**動いた押下だけ**が出るので、ただの選択では出ません） |
| `search` | 作業フォルダ全文検索（要件 7.7）。`asked`＝訊いた（`thread=0`ならスレッドが起動できずその場で検索した）、`found`＝表示した、`stale`＝古い問いへの答えだったので捨てた。**追い越しは画面に出ない**ので、順序はここでしか読めません |
| `session` | セッションの保存に失敗したとき（要件 8.5） |

## 検証

```powershell
cargo fmt --check
cargo check --offline
cargo test --offline
```

`run_check.bat`をダブルクリックすると上記を順に実行し、結果を`check_output.txt`へ書き出します。

依存パッケージをまだ取得していない環境では、最初の`cargo check`または`cargo build`にネットワーク接続が必要です。
